Hub Communication & Connection Lifecycle

How the builder hub routes messages and keeps at most one live connection per user, in sync with its session.

Problem

The builder hub is a transport-agnostic fan-out point for connected clients: it accepts payloads from any subscriber channel, broadcasts hub-wide messages, and tracks who is connected. Subscribers are addressed by topic rather than by transport, so a WebSocket socket is only the current client channel, not a built-in assumption. A client's connection must never outlive its session, and a user must never end up with two live connections. The hub achieves this with a single serial command loop, a split-by-class channel design so lifecycle signals are never lost, and a connection identity (connection_id) that lets both the in-memory state and the cross-instance Redis registry safely resolve "which connection is current".

Architecture — message flow

A client feeds the hub over two inbound channels of different classes; the hub's serial loop processes them and calls publish, which fans each message out to every subscriber whose topic set matches. Each subscriber owns an unbounded outbound channel drained by its WebSocket send task.

The split is deliberate. Payload (chat and other Workloads) is driven at the client's own rate, so it uses a bounded channel and errors when full — a slow or abusive client throttles only itself. Control (connect / disconnect / registry-change / shutdown) is bounded by the number of connections, not client traffic, so it uses an unbounded channel and is never dropped for back-pressure — lifecycle correctness must not depend on queue depth. Outbound is unbounded as well: once the hub accepts a message it is guaranteed delivered, and the only reason to drop a subscriber is a closed receiver. See services/hub/hub_service.rs · start for the biased loop and services/hub/connected_users.rs · publish for the fan-out.

Accepted residual risk: unbounded outbound can grow if a client stalls
Because the outbound per-subscriber channel is unbounded, a client that stops reading its socket while the hub keeps publishing will accumulate an unbounded queue in memory. This is accepted for now — lifecycle reliability is worth more than the bound. The intended mitigation is a read-idle / keepalive close that drops a subscriber that stops draining, rather than reintroducing a lossy bound on outbound.

Messages

Everything the hub broadcasts is a HubMessage, tagged by TopicKey so subscribers receive only the topics they asked for. Inbound, the two channels carry disjoint types: ControlCommand on the control channel and Workload on the payload channel.

Session & connection checking

Connection health is enforced at two scopes. In-memory, a single instance detects sessions that have expired and disconnects exactly the affected connection. Cross-instance, the Redis registry plus a periodic heartbeat reconcile connections a node no longer holds. Both scopes are fed by lifecycle events and both resolve identity by connection_id, so neither can tear down a fresher connection.

In-memory

A single ConnectionTracker owns one Hub-topic subscription and event-sources a user_id → (connection_id, session_key) map from UserConnected / UserDisconnected. Periodic consumers poll it via refresh_if_changed, which copies the map only when a monotonic generation counter advanced. The SessionChecker is one such consumer: on each tick it validates every tracked session against CurrentUserService and, on failure, issues a targeted disconnect(user_id, connection_id).

Cross-instance

The Redis registry holds one key per user, hub-connection:{user_id} → connection_id, with a TTL. Creating a connection SETs the key (replacing any prior value) and PUBLISHes the user id on the hub-registry-changed channel; removal DELs and publishes only when the connection id still matches. Every hub subscribes to that channel and re-checks the affected user. The HeartbeatTask walks the tracker's snapshot each interval and calls heartbeat_connection, which extends the TTL only when the stored id matches; a false result means the registry no longer holds this connection, so the task funnels a disconnect through the same CAS'd command path. invariant session_key is never written to Redis, logged, or placed in any broadcast payload — it stays in-memory only.

Last connection wins

Each user has at most one live connection. Every connect mints a fresh connection_id bound 1:1 to the session key that opened it, so identity is unambiguous. When a new connection arrives for a user who already has one, process(ConnectUser) publishes UserDisconnected for the old connection before recording the new one — the old socket sees its own id in the event and closes itself.

(C_A, S_A) active
ConnectUser{C_B, S_B}
UserDisconnected{C_A}
then record
(C_B, S_B) active

The safety property is the compare-and-remove on connection_id, enforced identically in memory (ConnectedUsers::disconnect with Some(id)) and in Redis (remove_connection_if_active, heartbeat_connection). A disconnect request — whether from a session expiry, a heartbeat miss, or a lagging socket — only removes the entry if the id still matches the active connection. So a stale disconnect(C_A) arriving after C_B has replaced it is a no-op, and the fresh connection is never dropped by an older session's cleanup.
